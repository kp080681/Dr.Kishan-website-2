## Overlap / Cannibalization Review

### Treatment overview vs condition pages

Current state:
- Homepage treatment sections introduce service categories and link to condition pages.
- Condition pages define individual terms.

Risk:
- Low if homepage remains a navigation and brand page.
- Medium if homepage metadata tries to target too many individual condition keywords.

Recommendation:
- Homepage should target broad surgeon/local/brand intent.
- Condition pages should target condition/procedure intent.
- Future umbrella pages, if approved, should target category intent.

### Condition pages vs blog articles

Higher overlap:
- `/conditions/varicose-veins`, `/conditions/varicose-veins-evla`, `/blogs/laser-treatment-varicose-veins`
- `/conditions/hernia`, `/conditions/hernia-surgery`, `/blogs/how-to-manage-a-hernia`
- `/conditions/piles-hemorrhoids`, `/blogs/how-to-prevent-hemorrhoids`

Recommended intent split:
- Condition pages: short, direct, appointment/service intent and term explanation.
- Blogs: longer informational education.
- Canonical/self-canonical and internal links should reinforce this split later.

### Condition page overlap inside the same topic

Varicose overlap:
- `/conditions/varicose-veins` should likely be canonical for the condition.
- `/conditions/varicose-veins-evla` can remain a procedure-specific explanation if metadata clearly targets EVLA.
- Do not create a third varicose-veins service page until this split is approved.

Hernia overlap:
- `/conditions/hernia` should likely carry condition intent.
- `/conditions/hernia-surgery` can carry procedure-term intent if retained.
- `/blogs/how-to-manage-a-hernia` should remain educational.
- Do not create a third hernia surgery page until overlap is resolved.

Appendix naming:
- `/conditions/appendix` explains appendix-related problems, including appendicitis.
- Search intent likely uses `appendicitis` or `appendix surgery`.
- ON_PAGE may improve metadata without changing route.
- Future alias/canonical to `/conditions/appendicitis` is possible, but not approved now.

### Blog redirects and legacy routes

Current:
- `/post/{oldSlug}` redirects exist only for the five public new posts because `getLegacyRedirects()` is based on `getBlogIndex()`.
- Migrated legacy posts remain in the content model but are not public.

Recommendation:
- Preserve current five redirects.
- TECH_SEO_QA should confirm redirect status codes.
- Do not expose migrated legacy posts without medical/content approval.
- If old indexed URLs exist for migrated posts, decide later whether to redirect them to the closest approved current page, return 404, or keep non-public.
